## 22. Логи и отладка

Цель: при любом сбое или некорректном поведении можно поднять детальный, машинно-читаемый след хода и точно увидеть, что пошло не так. Логи — **не проза** и **не пишутся моделью**.

### 22.1 Принципы

- **Пишет движок, детерминированно.** Модели (Ведущий/Режиссёр/валидатор) — субъекты логирования: движок фиксирует их входы, сырые выходы и метаданные, но не просит «описать, что было».
- **Структура, не проза.** Формат — **NDJSON** (одно событие = одна строка JSON), append-only, греп-абельно, диффабельно.
- **Сквозная корреляция.** Каждое событие несёт `session_id` и `turn_id` (+ при необходимости `arc_id`), чтобы проследить проблему от ввода до записи состояния.
- **Логи ≠ состояние.** Это отладочный артефакт; в каноне git его нет (полные промпты каждый ход раздули бы репозиторий). Хранится локально с ротацией.

### 22.2 Общая форма события

```
{ ts, session_id, turn_id, seq, type, level, payload }
```
`level` ∈ {`trace`,`debug`,`info`,`warn`,`error`}. `type` — из таблицы ниже. `payload` — структурированные поля под тип.

### 22.3 Типы событий (что фиксируется за ход)

| type | Что внутри (payload) |
|------|----------------------|
| `input` | ввод игрока (дословно); снимок дня/времени/локации; активные модули |
| `context_assembled` | RAG-запрос; top-k результатов с id и оценками близости; какие карточки NPC поданы; выдержки правил; оценка длины промпта в токенах |
| `mechanics` | каждый бросок: тип, базовый шанс, скрытые модификаторы, сырой d20, DC, результат; расчёт цены/времени/боя |
| `llm_call` | роль; запрошенная модель vs реально ответившая; ссылка/хэш отправленного промпта (полный текст — на уровне `debug`); сырой ответ; токены in/out; латентность; ретраи; сработал ли фоллбэк |
| `proposed_ops` | сырые `Op[]` от Ведущего (до валидации) |
| `validation` | что нормализовано, что отклонено/изменено и **почему** (напр. «отклонён `npc.alter_core`: нет причины»; «утечка знания: NPC сослался на `secret` факт F123») |
| `applied_ops` / `state_diff` | применённые операции + **дифф по сущностям before→after** (капитал 646→566; добавлен предмет id X; HP 38→30) |
| `worldsim` | сработавшие `seeds`/таймеры; какие условия совпали; тики мира |
| `persist` / `sync` | сохранение: git-commit hash, записанные файлы, `schema_version`; загрузка: checkout-коммит; конфликты синка; миграции схемы |
| `warn` / `error` | недоступность модели, провал парсинга, откат невалидной дельты, исключения |

### 22.4 Уровни детализации

Конфигурируемо: `info` (события + диффы + метаданные моделей) по умолчанию; `debug` добавляет полные промпты, сырые ответы и оценки ретривала; `trace` — всё. Полные промпты тяжёлые и содержат весь контекст хода — поэтому только на `debug`/`trace`.

### 22.5 Хранение, ротация, приватность

Локально (IndexedDB или директория логов рядом с состоянием), **вне каноничного git-состояния**. Ротация по числу ходов / дней / размеру. Логи содержат весь игровой контент и промпты → **не выгружать автоматически** никуда.

### 22.6 Bug-bundle (разбор инцидента)

Экспорт одним файлом: последние K ходов лога (на нужном уровне) + снапшот состояния на момент бага + конфиг (раскладка моделей, версии). Это то, что «поднимают и изучают» при сбое; можно приложить к репорту или скормить модели-анализатору (22.9).

### 22.7 Связь с `/ask`

`/ask` — **курируемое окно игрока** в тот же лог (раскрывает один бросок, состояние Силы числом, причину реакции NPC). Debug-лог — **полный сырой субстрат** под ним. То есть `/ask` читает лог, а не отдельную «кухню».

### 22.8 Диагностика пяти багов по логам

| Баг | Какое событие ловит |
|-----|----------------------|
| №5 предметы пропали | `state_diff` по `inventory` + `persist`/`sync` — видно, какая операция убрала предмет или сейв/загрузка дропнули его |
| №3 NPC знает лишнее | `context_assembled` (какие факты попали в контекст NPC) + `validation` (флаг утечки) |
| №4 дрейф NPC | `validation`/`applied_ops` по `npc.alter_core` — было ли несанкционированное изменение ядра |
| №2 забыл деталь | `context_assembled` — попал ли нужный факт в top-k и с какой оценкой (промах ретривала виден сразу) |
| №1 повтор сюжета | лог Режиссёра: какие `motifs_used` учтены, из какой комбинации осей выбрана арка |

### 22.9 Опционально — модель-анализатор логов (не автор!)

По запросу скормить bug-bundle сильной reasoning-модели (`openai/gpt-oss-120b` / `nvidia/nemotron-3-super-120b`), чтобы объяснить инцидент человеческим языком («почему NPC узнал героя»). Это **чтение** детерминированного лога, не его генерация; запускается вручную, в горячем пути хода не участвует.
