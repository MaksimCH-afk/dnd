# Патч к ТЗ: hosted-архитектура (v1.1 → v1.2)

**Назначение:** перевод развёртывания с local-first (PWA + git, движок в браузере) на hosted (тонкий клиент + app-сервер; состояние в Postgres/pgvector; эмбеддер и движок на сервере).
**Суть в одну строку:** браузер становится тонким клиентом (только UI); движок, состояние, эмбеддер и прокси к OpenRouter — на сервере; тяжёлые генеративные модели по-прежнему в OpenRouter (GPU не нужен).
**Затронуты разделы:** шапка, 3, 4, 6, 8, 10, 11, 15, 18, 19, 20, 22.

---

## ЧАСТЬ A. Шапка документа

- **Заголовок было:** «ТЗ: Текстовое НРИ (соло) — local-first PWA с движком состояния и LLM-связкой»
- **Заголовок стало:** «ТЗ: Текстовое НРИ (соло) — hosted-приложение с движком состояния и LLM-связкой»
- **Тип проекта было:** «self-hosted, local-first»
- **Тип проекта стало:** «self-hosted: app-сервер + тонкий клиент в браузере»
- Версия: 1.1 → **1.2 (hosted-архитектура)**.

## ЧАСТЬ B. Раздел 3 «Архитектура и развёртывание» — ЗАМЕНИТЬ ЦЕЛИКОМ

**Модель: hosted — тонкий клиент в браузере + app-сервер.** Один URL открывается и на ПК, и на Android → кросс-девайс решается сам собой. Тяжёлые генеративные модели — в OpenRouter (сервер их не крутит, GPU не нужен).

```
┌─────────────────────────────────────────────┐
│  Тонкий клиент (браузер/PWA: ПК и Android)    │
│  • только UI: хроника, композер, панели       │
│  • шлёт ввод игрока, получает прозу + дельты   │
│  • состояние/движок/эмбеддер НЕ здесь          │
└───────────────┬───────────────────────────────┘
                │ WebSocket/SSE (стрим прозы + обновления состояния)
                ▼
┌─────────────────────────────────────────────┐
│  App-сервер (Docker)                          │
│  • ДВИЖОК: сборка контекста, броски, механика, │
│    оркестрация ролей, валидация, дельты, логи  │
│  • Эмбеддер bge-m3 (CPU) → RAG                 │
│  • Прокси к OpenRouter (ключ, ретраи, фоллбэк) │
│  • API: ход, сейв/загрузка, кампании, /ask     │
└──────┬───────────────────────────────┬────────┘
       │                               │
       ▼                               ▼
┌──────────────────────┐      ┌─────────────────────┐
│ Postgres + pgvector   │      │  OpenRouter API      │
│ состояние, сессии,     │      │  (модели по ролям)   │
│ NPC, факты, хроника,   │      └─────────────────────┘
│ векторный индекс, логи │
└──────────────────────┘
   (опц.) git/gdrive — бэкап и md-экспорт, не источник синка
```

**Размещение движка (следствие тонкого клиента).** Раз состояние, эмбеддер и индекс на сервере, движок тоже на сервере — иначе тонкий клиент кругло-рейсил бы за каждым фактом. Клиент тонкий; «тяжесть» — на сервере. Backend здесь не «тонкий прокси», а app-сервер.

**Источник истины — Postgres** (состояние/сессии/NPC/факты/хроника + pgvector-индекс + логи). Кросс-девайс не требует ручного синка: оба устройства работают с одной БД. git/gdrive остаётся **опциональным** слоем бэкапа и md-экспорта, но больше не механизм синхронизации.

**Серверные специи (один пользователь):** GPU не нужен. Базово 1 vCPU / 1 ГБ хватает на статику + прокси; комфортно с эмбеддером bge-m3 на CPU + Postgres/pgvector — **2 vCPU, 4 ГБ RAM, 20–40 ГБ диска**. Нагрузка backend — I/O-bound (ждёт OpenRouter и стримит), эмбеддер — единственный реальный compute, лёгкий на CPU. Скорость хода упирается в OpenRouter, не в железо сервера. (Подробные требования — Часть C.)

**Стек (ориентир):** клиент — TypeScript + лёгкий фреймворк (Svelte/React), может остаться PWA-оболочкой (но онлайн-зависимой); транспорт — WebSocket или SSE; app-сервер — Node/Python, движок + оркестрация; эмбеддер — `bge-m3` (или `multilingual-e5`) на CPU; БД — Postgres + pgvector; всё в Docker (compose: сервер + Postgres). Развёртывание — твой VPS/коробка.

**Компромиссы:** небольшая регулярная плата за VPS; нужно поддерживать сервер; данные на сервере (для приватной игры ок, если это твой VPS); онлайн обязателен (тонкий клиент без сервера не играет).

## ЧАСТЬ B. Точечные правки в остальных разделах

### Раздел 4 (модель состояния — вводный абзац)
- **Было:** «Состояние = типизированные сущности в JSON (по файлу/коллекции в git-репо) + рендер в md…»
- **Стало:** «Состояние = типизированные сущности в **Postgres** (источник истины; pgvector для индекса) + опциональный md/JSON-экспорт для чтения/бэкапа.»

### Раздел 6 (роли — строка «Эмбеддинги»)
- **Было:** «локальный `bge-m3` (или `multilingual-e5`), сменный … Векторизация/поиск…»
- **Стало:** «`bge-m3` на сервере (CPU; или `multilingual-e5`), сменный … Векторизация/поиск … (pgvector)»

### Раздел 8 (поток хода — шаг 8 «Персист»)
- **Было:** «Персист: IndexedDB; по `/save`/автосейву — экспорт JSON+md и `git commit`.»
- **Стало:** «Персист: транзакция в Postgres; по `/save`/автосейву — снапшот точки сохранения (+ опц. md-экспорт/бэкап).»

### Раздел 10 (RAG)
- **Было:** «…класть в локальный векторный индекс (рядом с состоянием/в IndexedDB; пересборка из git при синке)…»
- **Стало:** «…эмбеддить (эмбеддер на сервере) и класть вектор в **pgvector**…» (остальное про top-k и русский recall — без изменений)

### Раздел 11 (`/go`, `/save`)
- **`/go` было:** «`git pull` → собрать `session`…»
- **`/go` стало:** «открыть кампанию → собрать `session` из Postgres…»
- **`/save` было:** «экспорт JSON-канона + md-рендер → `git commit`…»
- **`/save` стало:** «зафиксировать точку сохранения (снапшот состояния на сервере; опц. md-экспорт)…»

### Раздел 15 «Сохранение, загрузка, синхронизация» — ЗАМЕНИТЬ ЦЕЛИКОМ
- **Канон — Postgres на сервере.** `schema_version`; при изменении схемы — **миграции БД** (обязательно). md/JSON-экспорт — опциональный человекочитаемый бэкап.
- **Новая игра** — флоу раздела 5. **Продолжить** — выбрать кампанию из списка на сервере (или импорт сейв-бандла zip — для переноса).
- **Мульти-кампании:** отдельные записи кампаний в БД; UI даёт список.
- **Кросс-девайс — без ручного синка:** ПК и планшет работают с одной серверной БД; «продолжить с того же места» = просто открыть кампанию. (Конкурентный доступ с двух устройств — последняя запись побеждает; для соло-игры некритично.)
- **Точки сохранения / откат:** `/save` и автосейв создают именованные снапшоты состояния (server-side); «к Дню X» = восстановление снапшота. Опционально — периодический git/gdrive-бэкап БД-дампа.
- Файлы правил — read-only.

### Раздел 14 (смерть)
- **Было:** «откатиться к более раннему коммиту (git checkout — честный „загруз“)…»
- **Стало:** «восстановить более ранний снапшот (честный „загруз“)…»

### Раздел 18.5 (компоненты — индикатор и онбординг)
- Индикатор «синка» → **индикатор соединения с сервером**.
- Экраны сейвов: «Продолжить — список кампаний с сервера/импорт; список снапшотов = точки сохранения».
- Онбординг: **ключ OpenRouter и выбор моделей — в конфиге сервера (один раз администратором)**; в клиенте — выбор/создание кампании; настройки (модель на роль, эмбеддер, тема, размер текста).

### Раздел 18.6 «Связь с backend (контракт)» — ЗАМЕНИТЬ ЦЕЛИКОМ
Клиент тонкий: только UI. Движок, состояние и эмбеддер — на app-сервере. Клиент общается с сервером на **игровом уровне** (не на уровне отдельных LLM-вызовов — те оркеструет движок на сервере).

**API клиент↔сервер (игровой уровень):**
- `WS /play` (или `POST /turn` + SSE): ввод игрока → стрим прозы + по завершении дельты состояния и обновлённый статус.
- `GET /campaigns`, `POST /campaigns`, `POST /campaigns/{id}/load`, `POST /campaigns/{id}/save`.
- `GET /ask?turn=…` — данные мета-режима из лога (раздел 22).
- `GET /health` — соединение + раскладка моделей.

**Внутри сервера (не виден клиенту):** движок зовёт OpenRouter по ролям (`narrator|validator|director`) с ключом, ретраями и фоллбэком; эмбеддер и pgvector — локально на сервере.

**Поток UI:** ввод → реплика сразу в хронику (оптимистично) + «Мастер пишет…» → стрим прозы с сервера → по завершении дельты → гроссбух анимирует дифф, статус из состояния (не из прозы) → тост «Сохранено — День X». Режиссёр — на сервере вне горячего пути.

### Раздел 19 (нефункциональные)
- **Латентность:** «локальный RAG» → «RAG на сервере».
- **Приватность ключа было:** «в backend; прямой вызов из PWA — опционально».
- **Приватность ключа стало:** «ключ OpenRouter только на сервере; в клиент не попадает».
- **Офлайн было:** «оболочка и состояние офлайн; LLM-ходы требуют сети».
- **Онлайн стало:** «тонкий клиент без сервера не играет; при потере соединения — понятное сообщение, ввод не теряется. Офлайн-режима нет — следствие hosted-модели.»
- **Добавить:** «Доступность сервера: один пользователь, но сервер должен быть поднят; бэкап БД на случай сбоя.»

### Раздел 20 (этапность — Фаза 0)
- **Было:** «PWA, backend-прокси, git-синк, конфиг ролей, первый запуск…»
- **Стало:** «app-сервер (Docker) + Postgres/pgvector + эмбеддер на сервере, прокси к OpenRouter, конфиг ролей, тонкий клиент по WS/SSE, NDJSON-логирование…»

### Раздел 22 (логи)
- 22.1: «в каноне git его нет … хранится локально» → «хранится на сервере отдельно от каноничного состояния».

## ЧАСТЬ C. Требования к серверу

Генеративные модели — в OpenRouter, поэтому **GPU не нужен**. Единственный реальный compute на сервере — эмбеддер (bge-m3, ~0,5 млрд параметров) на CPU + Postgres. Нагрузка прокси — I/O-bound.

### C0. Выбранная конфигурация (решено)

- **Тариф:** Optimal AMD — **2 vCPU / 5 ГБ RAM / 35 ГБ NVMe** (≈ 8.48 €/мес). Соответствует «рекомендуемому» тиру с запасом по RAM; NVMe — плюс для Postgres/pgvector.
- **ОС:** **Ubuntu 24.04 LTS**.
- **Сеть:** обычный **IPv4** (опцию «Только IPv6» НЕ включать — см. C3).
- **Период:** помесячно на старте.

### C1. Железо (ориентиры по тирам)

| Тир | CPU | RAM | Диск | Комментарий |
|-----|-----|-----|------|-------------|
| Минимум | 1 vCPU | 2 ГБ | 20 ГБ SSD | работает; эмбеддер лучше квантовать (int8/ONNX), иначе чуть медленнее |
| **Рекомендуемо** | **2 vCPU** | **4 ГБ** | **40 ГБ SSD** | комфортно; ≈ дешёвый VPS (Hetzner CX22 и аналоги, ~€4–8/мес) |
| С запасом | 4 vCPU | 8 ГБ | 60 ГБ SSD | место под более крупный эмбеддер, быструю переиндексацию, рост |

Память по компонентам: bge-m3 резидентно ~2,2 ГБ (fp32) / ~1,1 ГБ (fp16) / ~0,6 ГБ (int8); Postgres — сотни МБ; app-сервер — сотни МБ; ОС. Диск: ОС ~5–8 ГБ, Docker-образы ~3–5 ГБ, веса эмбеддера ~2 ГБ, данные кампаний растут медленно (текст — десятки-сотни МБ; векторы bge-m3 dim 1024 ≈ 4 КБ/запись), логи с ротацией. **SSD обязателен** (латентность Postgres и векторного поиска).

### C2. Софт

- ОС: **Ubuntu 24.04 LTS** (выбрано; LTS до 2029, свежие пакеты, вся документация готова).
- Docker + docker-compose.
- Postgres 16 + расширение **pgvector**.
- App-сервер: Node 20+ или Python 3.11+.
- Эмбеддер-рантайм: HF `text-embeddings-inference`, либо sentence-transformers/ONNX. На CPU рекомендуется int8/ONNX-квантизация для скорости.
- Reverse-proxy + TLS: Caddy (проще всего, авто-Let's Encrypt) / nginx / Traefik.

### C3. Сеть

- Исходящий HTTPS к OpenRouter — обязательно открыт.
- Разовый исходящий к Hugging Face для загрузки весов эмбеддера (или зашить в образ).
- Входящий — только порт приложения за reverse-proxy.
- Трафик мизерный (стрим токенов) — любой тариф подойдёт.
- Латентность важнее до OpenRouter, чем до тебя (скорость хода упирается в OpenRouter). Бери EU-регион (Вена → любой EU-VPS — ок).
- **Только IPv4 (опцию «Только IPv6» НЕ включать).** При IPv6-only сервер рискует не дозвониться до OpenRouter (его API часто только по IPv4), а также до Hugging Face/Let's Encrypt/Docker-реестров; плюс доступ с мобильных сетей без IPv6 ненадёжен. Экономия 1 €/мес не оправдана.

### C4. Доступ и безопасность (важно для приватной игры в сети)

- **Рекомендуемый доступ — Tailscale** (или другой WireGuard-VPN): сервер не торчит в публичный интернет, нет открытых портов и возни с авторизацией, трафик шифрован. Идеально для приватного одиночного инструмента со зрелым контентом.
- **Альтернатива — публичный доступ:** тогда **обязательна** аутентификация (basic-auth / токен / OAuth), иначе боты и случайные люди сожгут твои кредиты OpenRouter и прочитают данные. Плюс домен/динамический DNS и TLS.
- Секреты: ключ OpenRouter — в env/секрете сервера, никогда в клиенте.
- Бэкапы: периодический `pg_dump` по cron в git/gdrive/объектное хранилище (раздел 15 ТЗ).

### C5. Альтернативы VPS

- **Домашняя always-on коробка / мини-ПК / Raspberry Pi 5 (8 ГБ).** Работает (ARM; bge-m3 идёт на ARM CPU — проверить, что рантайм эмбеддера поддерживает ARM). Бесплатно, если железо есть; доступ извне — через Tailscale (снимает вопросы публичности и аптайма дома).
- **Managed Postgres с pgvector** (напр. Supabase), если не хочешь держать БД сам — но для одного пользователя проще и дешевле поднять Postgres в том же docker-compose.
